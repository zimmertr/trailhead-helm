# 0003. Each service connects to the database as its own login, from a Secret made by hand

- Status: Accepted
- Date: 2026-11-12
- Decider: TJ, 2026-11-12, in trailhead's PRD: one Postgres from CloudNativePG, with per-service database roles.
- Issues and PRs: #3
- Cited in code as: none
- Guide: [`CLAUDE.md`](../../CLAUDE.md), Rules

## Context

`api`, `admin` and the fetcher share one database and need different rights: `api` reads and adds register entries, `admin` updates them, and the fetcher writes project numbers.

## Decision

- `database.cluster.roles` declares `trailhead_api`, `trailhead_admin` and `trailhead_fetcher` as CloudNativePG managed roles. The api and admin roles get `pg_read_all_data`; the fetcher's gets `pg_write_all_data` too.
- Each role's password is a `kubernetes.io/basic-auth` Secret created by hand, as Bluebird's preview login is. The chart reads its name from the role and builds `DATABASE_URL` from its keys.
- The INSERT for `api` and the UPDATE for `admin` are table grants, which belong in the app's migrations.

## Evidence

- 2026-11-12: CloudNativePG 1.30's `Database` resource manages schemas, extensions and foreign data wrappers, and its roles take `inRoles`, but neither grants privileges on a table (`kubectl explain`).
- 2026-11-12: Bluebird's `bluebird-database-preview` Secret is `kubernetes.io/basic-auth`, made with `kubectl create`.

## Alternatives rejected

- `postInitApplicationSQL` with default privileges: it runs once, when the cluster is created, so a change to it would never reach a running database.
- Secrets generated by the chart: Argo CD renders without `lookup`, so each sync would make a new password.

## Consequences

- Three Secrets to create by hand in each namespace before the services can connect.
- Until the migrations grant them, `api` cannot insert and `admin` cannot update.
